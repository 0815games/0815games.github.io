# Host reload recovery — implementation in progress

The live Firebase match still cannot resume after a host reload. `restorePartyHost` is a tested simulation building block, not a complete recovery system. It requires a checkpoint from trusted storage; it checks the locked roster, mode and teams, resets all presence and held movement, cancels queued inputs, and retains receipts. The browser host is not a trusted anti-cheat authority.

An experimental Firebase recovery store and complete draft rules now exist. The emulator covers atomic checkpoint/view records, generation takeover, stale-owner writes, member read isolation and an experimental host/guest handoff with an uncommitted input. Experimental durable host and generation-aware client sessions now delay acknowledgements until persistence and reconcile or reject outstanding commands on takeover. The branch contains the experimental adapter and host resume control, and emulator tests cover host reload in all five roster/mode combinations. The recovery path and resume button are explicitly disabled by default so campaign can be released without enabling unfinished recovery. **The branch and rules are not published**, and they do not yet guarantee safe end-to-end recovery. In particular, a crash during takeover and reading a cached checkpoint need explicit handling; the old live view paths are not fenced by these experimental rules.

A safe online handoff still needs all of the following before it is enabled:

1. A durable checkpoint bound to the immutable party ID and started manifest, with an explicit version and bounded size. Account for versus lanes and four-player state. A recipient snapshot is not a full checkpoint.
2. A Firebase-enforced, atomic host generation/lease with a unique connection identity. Old hosts must be fenced from **every** checkpoint, view and input-acknowledgement write. A same-browser Web Lock is not cross-device fencing.
3. Harden and performance-test the experimental durable host session in the actual game: publish checkpoint, generation and recipient views as one consistent commit. A guest must never be acknowledged for a command that a checkpoint can later roll back. Preserve the command sequence and receipts, and define behaviour when a checkpoint cannot be saved; pause rather than silently claim success.
4. Validate the branch’s host-reconnect UI and generation-aware client on actual devices and networks. The host must recover the same party, not accidentally create a second simulation. Guests must recognise only a verified newer generation, stop local input during handoff, reconcile outstanding commands against durable receipts, and reject stale generation writes/views. Current live clients intentionally fail on an epoch change.
5. Firebase emulator tests for host refresh across 2/3/4-player modes, stale host after takeover, two concurrent hosts, guest pending command, stale/reordered writes, checkpoint size and malformed checkpoints, and permissions. Then test actual devices and flaky networks. If fencing or checkpoint persistence fails, end/pause with a clear message, not an unsafe restore.

Replacing Firebase Realtime Database rules requires the complete combined ruleset, not a partial fragment. Do not enable a new storage path or ask for production publication until the complete rules and the handoff have passed those tests. Separately, player-hosted simulation and XP remain client-controlled and unsuitable for trusted competitive outcomes.

## Bandwidth and latency gate

The current prototype writes a complete checkpoint and all player views up to ten times per second. A simple idle four-player simulation produced about 13.9 KB per commit (roughly 500 MB/hour written at that rate), before Firebase protocol overhead, guest downloads, or combat growth. This is an illustrative local measurement, not a billing estimate. Measure real network conditions and billing, and reduce or otherwise explicitly budget the traffic before deploying widely. Slow database commits can slow simulation because the prototype serializes writes.
