# Firebase setup

The game uses Firebase Authentication (email/password) and the existing Realtime Database. `database.rules.json` is a complete, deny-by-default ruleset for this prototype, NOT a rules fragment. Before publishing it, inspect the existing database rules and merge the `players` subtree if the database contains other applications or data; publishing the file as-is replaces all database rules. Publish the resulting rules in Firebase Console → Realtime Database → Rules (or use the Firebase CLI with the correct project and database instance). The repository cannot deploy rules by itself.

Ensure Authentication → Sign-in method has Email/Password enabled. Password reset emails use the Firebase Auth configuration. Profile creation and XP sync require the rules to be published. Profiles are owner-readable/writable, with immutable name/gender and validated XP. Client-side XP is **not cheat-proof**: an authenticated player can submit arbitrary increases. Do not use it for competitive leaderboards. Server-authoritative rewards and validation are future work. Runs themselves are not saved. The game currently assumes one active run per account; concurrent tabs/devices may award XP for separate runs.


## Player-hosted co-op (not enabled)

`../firebase-party-channel.mjs` is an experimental low-level Realtime Database packet channel, not a complete party system. It takes the modular Firebase SDK as an injected dependency, sends each player's latest input under their own path, and lets a host publish both player views atomically. JSON string encoding preserves empty arrays through Realtime Database; packet sizes are bounded and writes are serialized. Tests use an in-memory SDK mock, not a Firebase emulator or live project. The current database rules deny all `parties` access and have not been changed.

Before enabling: design and emulator-test immutable host/membership and private invitations; enforce host-only view writes and each authenticated user's own input writes in Realtime Database rules; implement presence/onDisconnect, host lifecycle and timeouts, one-outstanding-command/receipt reconciliation, lobby creation and cleanup, UI, and real-account testing. Client-side checks in the channel are convenience checks, not access controls. Do not publish permissive rules or send private player profiles to other users. A player-controlled host is not trusted for anti-cheat or rewards. Firebase usage and costs depend on polling, write frequency, and session size; measure and bound them before a public release.

### Private party code client (experimental)

`../firebase-party-lobby.mjs` provides low-level primitives for a random 128-bit hex party code, atomically reserving a host UID and claiming a single guest slot with Firebase transactions. It is connected to the disabled party UI and covered by both mock and Firebase emulator tests. A party code is a bearer secret; never expose it in logs, referrers, query strings, or as a token destination. Membership is **not protected by the client module**. Current rules deny this entire database path.

A complete deployment must provide emulator-tested rules binding the owner and guest to authenticated UIDs, limiting who can read or write each party path, preventing unauthorized slot claims and cross-player input writes, protecting snapshots and profile data, and handling simultaneous join/leave and stale sessions. Hosting a party does not grant the host access to another player's private profile. Also required: presence with safe disconnect handling, cleanup, replay/receipt handling, UI, and real Firebase testing. Do not deploy or enable this client until those pieces are finished and reviewed.

### Experimental party session controller

`../firebase-party-session.mjs` connects the player-hosted protocol to the packet channel. The host advances while the host is online; a disconnected guest is suspended without stopping the host. Player-specific views indicate whether each participant can issue commands. The client permits one sequenced command at a time, waits for an applied/cancelled receipt, and locks out further commands if a write or timeout leaves the outcome uncertain. A changed host epoch fails closed rather than silently accepting state from another session. Tests use mock channels, not Firebase.

This controller is **not alpha-ready or wired to the UI**. It does not implement Firebase presence, validate Firebase rules, create lobbies, schedule its own ticks, handle reconnect/host migration, establish authenticated epochs, or award rewards. In particular the caller must generate a fresh unpredictable epoch per host session, supply trusted presence, and stop/restart the controller after an epoch change. A stale final `ready` view can remain after host/network failure until presence handling is added. Do not enable this code until security rules, lifecycle and real Firebase behavior are tested.

### Experimental Firebase presence

`../firebase-party-presence.mjs` registers `onDisconnect().remove()` before marking a connection online, uses per-connection random IDs and server timestamps, refreshes a heartbeat, and treats old timestamps as offline. It reports all players offline while its Firebase connection is down, fails closed on listener errors or account changes, and feeds presence changes into the host session to pause only when the host is unavailable. Automated tests use a mock SDK, including delayed registration and reconnect cases. Defaults are a five-second heartbeat and a twenty-second expiry; the two clients together generate roughly 24 heartbeat writes per minute, in addition to match snapshots and commands.

This is **not yet safe to enable**: it requires tested rules restricting presence writes to the authenticated participant and reads to party members, actual Firebase/onDisconnect testing, connection and party cleanup, and UI integration. Presence is best-effort, not proof of fair play; network delays or mobile background throttling can temporarily mark a live player offline. SDK writes queued through a disconnect may briefly leave a stale connection record until its heartbeat expires. Abandoned party records also need a cleanup strategy. Measure bandwidth and Firebase usage before release.

### Draft alpha rules and emulator tests

`party-alpha.draft.rules.json` is a **separate, unapproved draft**, not the live `database.rules.json`. It keeps existing player rules and sketches authenticated, code-based party membership, own-input writes, host-only view publication and member presence. Party codes are high-entropy bearer secrets: anyone authenticated who learns a code can inspect the host/guest slot and, if vacant, claim it. Do not put codes in URLs or logs. The hosting player can still modify their own match state, and existing XP remains client-writable.

The draft now allows only the host to delete the whole party atomically; emulator tests also check that this does not grant the host unrestricted parent writes. However, the draft is not deployable alpha infrastructure yet: there is no automatic retention policy, guest replacement/session fencing or abandoned-party cleanup; malicious participants can generate costs or tamper with their allowed inputs/presence; rules cannot validate gameplay. Security and lifecycle review, client integration, Firebase quotas, and real-account tests remain necessary. Before any limited private test, follow `ALPHA-RULES-REVIEW.md` and explicitly accept its unresolved abuse, cost and cleanup risks. Publishing a rules file replaces the database rules.

`rules-test/` contains Firebase Realtime Database emulator tests for the draft, including authenticated and unauthenticated access, slot claims, input/view privacy, packet limits, presence and existing profile isolation. Run `npm ci && npm test` there with Node 22, Java 21, and network access to download the database emulator. The GitHub Actions workflow runs the same tests on changes. These tests do not touch the live Firebase project and cannot prove the full application is secure.


### Party setup UI prototype

The page includes a **disabled-by-default** party panel for creating, copying, joining and leaving party codes. Its host start action now connects the Firebase adapter to the battlefield; participants publish only a match-specific name, gender and level, never private XP. The explicit feature flag in `account.js` must remain false until the full match flow, lifecycle, rules and real-account testing are complete. The code is a bearer secret and is never put in a URL. Sign-out now attempts to stop the match and remove the party or guest slot before signing out, with a two-second limit so an offline connection cannot trap the user. A transaction already in flight, a timeout, a crash or a closed browser can still leave an abandoned party; serverless automatic cleanup remains unresolved.

The emulator suite now exercises two authenticated clients running the hosted match, issuing commands, disconnecting and reconnecting. It is still not a live Firebase or physical-device test. No draft rules have been deployed.


### Experimental game-facing adapter

`../firebase-party-game.mjs` composes the Firebase packet channel, the presence layer and player-hosted simulation into a game-facing adapter. It accepts an already established roster and explicitly supplied players; it does not itself establish membership, load player profiles, or start a lobby match; the disabled party panel performs that handoff. Local presence and the host's latest view must both indicate readiness before accepting commands. The emulator suite exercises two adapters, shared building, starting a wave and a network disconnect/reconnect. The adapter is still disabled and must not be used against live Firebase before the rules and complete lifecycle are reviewed. It reports failure but the caller must call `stop()` to release resources. Each adapter is single-use.


### Connected experimental flow

The host creates a private party and publishes a minimal match profile. The guest joins and publishes their own match profile. The host starts once both profiles exist; a one-time `startedGuest` marker locks the roster, and both clients attach the Firebase adapter to the shared battlefield. The host can close the party; a guest leaving atomically removes their slot, match profile and last input. The host waits for the guest profile before enabling start. If that guest leaves after start, their soldier is suspended while the host continues the same battle; the same guest can rejoin using the party code. Currently the guest must join once before the host starts the match, and a different guest cannot replace them during that match. Security rules do not force all clients to use the cleanup operation, so malicious or crashed clients can leave stale data. These additions require the **draft** rules; the deployed rules are unchanged and deny party access. The flag in `account.js` remains off. Before any limited private deployment, follow `ALPHA-RULES-REVIEW.md`; automated cleanup and live-account testing remain unresolved.
