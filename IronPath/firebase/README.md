# Firebase setup

The game uses Firebase Authentication (email/password) and the existing Realtime Database. `database.rules.json` is a complete, deny-by-default ruleset for this prototype, NOT a rules fragment. Before publishing it, inspect the existing database rules and merge the `players` subtree if the database contains other applications or data; publishing the file as-is replaces all database rules. Publish the resulting rules in Firebase Console → Realtime Database → Rules (or use the Firebase CLI with the correct project and database instance). The repository cannot deploy rules by itself.

Ensure Authentication → Sign-in method has Email/Password enabled. Password reset emails use the Firebase Auth configuration. Profile creation and XP sync require the rules to be published. Profiles are owner-readable/writable, with immutable name/gender and validated XP. Client-side XP is **not cheat-proof**: an authenticated player can submit arbitrary increases. Do not use it for competitive leaderboards. Server-authoritative rewards and validation are future work. Runs themselves are not saved. The game currently assumes one active run per account; concurrent tabs/devices may award XP for separate runs.


## Player-hosted co-op (not enabled)

`../firebase-party-channel.mjs` is an experimental low-level Realtime Database packet channel, not a complete party system. It takes the modular Firebase SDK as an injected dependency, sends each player's latest input under their own path, and lets a host publish both player views atomically. JSON string encoding preserves empty arrays through Realtime Database; packet sizes are bounded and writes are serialized. Tests use an in-memory SDK mock, not a Firebase emulator or live project. The current database rules deny all `parties` access and have not been changed.

Before enabling: design and emulator-test immutable host/membership and private invitations; enforce host-only view writes and each authenticated user's own input writes in Realtime Database rules; implement presence/onDisconnect, host lifecycle and timeouts, one-outstanding-command/receipt reconciliation, lobby creation and cleanup, UI, and real-account testing. Client-side checks in the channel are convenience checks, not access controls. Do not publish permissive rules or send private player profiles to other users. A player-controlled host is not trusted for anti-cheat or rewards. Firebase usage and costs depend on polling, write frequency, and session size; measure and bound them before a public release.
