# Iron Path: co-op foundation and roadmap

## Goal and current status
One authoritative shared match for one or two authenticated players, using the same rules for solo and co-op. This is an incremental migration of the existing prototype: **online co-op does not exist yet and the match is not cheat-proof**.

## Started: command rules
`match.mjs` is a DOM- and Firebase-independent command layer. `simulation.mjs` contains the fixed-step shared movement, enemy waves, attacks, cooldowns and outcomes. The solo UI executes this simulation; replay and two-player simulation tests run without a browser. The current solo game uses it for build, upgrade, tap-to-move, and airstrike. It models player-specific positions/cooldowns and a shared bunker economy and shared towers. Either participant may upgrade a shared tower. Each tower records its builder. Automated tests exercise two players, invalid inputs, shared resources and independent cooldowns. The server must supply the player identity from the authenticated connection; an ID sent in a command is not proof of identity.

## Started: protocol core
`protocol.mjs` provides an in-memory, versioned server-side protocol adapter around the existing simulation. The host supplies the authenticated player ID separately from the command, accepts contiguous per-player sequence numbers, orders accepted commands by server receipt before each fixed tick, caches bounded receipts for safe retries, and provides detached client snapshots and trusted server checkpoints. Reconnection can resume from a snapshot/checkpoint without applying queued commands twice. Tests cover two players contending for a pad, retry conflicts, gaps, queue limits, checkpoints and reproducible replay.

This module is **not a deployed server**. Checkpoints are trusted server storage only, never accept them from clients. The experimental transport verifies Firebase ID tokens and a preconfigured roster and rate-limits inputs. A production deployment must provide lobby membership, scale-safe rate limiting, and securely persist checkpoints and rewards. It pauses and neutralizes movement on disconnect, but needs timeout policies, durable event/reward idempotency, protocol/engine version compatibility, bandwidth control and production recovery. Snapshot results currently expose match state and only the requesting player's receipt history; delivery, authentication and privacy enforcement are the transport's responsibility. Receipts have a bounded history, so clients must resync from a fresh snapshot when an old retry expires.

## Started: experimental transport
`server/` contains an experimental single-match WebSocket service with Firebase Admin token verification, an explicit roster, origin checks, command limits and pause/reconnect behavior. Its network tests use mock authentication, not live Firebase. It is not deployed, has no lobbies or durable state, and does not secure existing client-writable XP. See `server/README.md` before running it. Real hosting, durable reward processing, security review and production integration remain necessary.

## Started: client transport adapter
`coop-client.mjs` connects to the experimental match service with an injected Firebase token provider, uses snapshots and command receipts, and reconnects with bounded retries. It serializes commands, refuses uncertain blind retries, and requires a fresh snapshot after a command timeout. A network integration test exercises two clients and reconnection; authentication is mocked in those tests. An opt-in UI adapter now renders two players and sends commands against server snapshots, but it is disabled by default and no hosted co-op service is available yet. See `server/README.md` for limitations and trusted endpoint configuration.

## Started: private lobby rules
`server/lobby.mjs` adds a server-side, in-memory two-player lobby state machine with short-lived, single-use invitation secrets and a trusted match roster. Tests include the local WebSocket match service with mock authentication. An experimental HTTP adapter verifies injected bearer-token identities and enforces an Origin allowlist and process-local per-identity limits; real HTTP tests use mock authentication. An optional experimental in-process allocator now connects the owner’s start request to a trusted roster and match launcher, tested end to end with local HTTP and WebSockets using mock authentication. It is not deployed or connected to the UI; there is no production launcher or match routing. It still needs live Firebase verification, atomic shared storage, edge/distributed abuse controls, complete match lifecycle, and recovery before players can use it.

## Next milestones
1. Continue hardening the shared fixed-step simulation and command API. Keyboard movement and starting waves now use the command boundary, and the simulation advances every player independently. Continue testing full matches and refine target ordering and event handling. Speed and pause remain local UI controls; define their co-op permissions before networking. The experimental opt-in UI renders both players, but profile/reward persistence still assumes one local player and there is no publicly playable online mode. Player level is captured at the start of a wave in the current solo adapter; a future authoritative service must load trusted stats.
2. Extend the versioned snapshot and ordered-command core with a real transport, disconnect handling and durable reconnect/recovery tests. Avoid trusting client timestamps or allowing clients to write match state or award their own rewards. Account for duplicate, delayed, out-of-order and invalid commands.
3. Run that engine on an authoritative, long-lived game service. Authenticate both players with Firebase ID tokens, enforce lobby membership and rate limits on the server, and persist validated results with Admin credentials. Evaluate hosting and cost before choosing the service. Cloud Functions are appropriate for bounded account/invite operations, not assumed to be a continuously running real-time match host.
4. Build private lobbies/invites, join/leave/reconnect, timeouts and two-player UI; add narrowly scoped Firebase rules for each new data path and integration tests. Do not expose active authoritative state as client-writable database data.
5. Build skill allocation and stat aggregation as shared, versioned graph rules, including self/ally/shared-defense effect scopes. Validate allocations and refunds with a trusted server transaction; test connectivity and cross-player effects. Keep existing profile XP compatible.
6. Test online sessions on real phones, desktop, poor networks and across devices; measure latency, failure recovery and infrastructure cost before release.

**Existing XP remains client-awarded and modifiable.** The current Firebase rules provide account isolation but do not validate fair play. No existing database rules were changed by this foundation. None of the shared code becomes secure merely by running in a browser.
